    ⚠ These actions move things on the motorcycle

    Actuator tests energise real outputs — injectors squirt fuel, coils make sparks, the fuel pump pressurises the rail. Adaptation resets discard learned values and cannot be undone. Every action below shows exactly which preconditions pass and which do not.

    Adaptations and routines

    Actuator tests

    IAW ECUs have no output timer: an output stays energised until something turns it off. This workstation owns the deadline and releases on expiry, on disconnect, and if the browser goes away.

    🧪 This drives the simulated motorcycle, not a real one

    Everything on this page changes the bike the workstation is talking to, never the workstation's own behaviour. Seeded faults move the live channels first and only mature into fault memory afterwards, so you can practise reading the data before the code shows up — and watch a code come straight back if you clear it while the cause is still there.

    Comms quality

    The adapter and the wiring are part of the job. These make the simulator behave like a bad connection so the retry, checksum and timeout paths get exercised on purpose.

    Seeded faults

    Each fault changes the physics, and the code it eventually stores is listed with it. Nothing appears in fault memory straight away.

    What a guided test is

    A single actuator pulse is a twitch. A procedure puts the engine in a known state, does one bounded thing, watches the right channels and says what the result means. Observations are ordinary live reads; anything that moves on the bike goes through the same safety gate and the same output deadline as the Service view. The verdict at the end is an interpretation — a place to start looking, not a diagnosis.

    CAN identifier discovery

    CAN-era bikes use a CAN diagnostic path, but ISO-TP, CAN IDs, and the application protocol are not assumed to match K-Line. This offline analyzer can identify likely pairs in an existing capture; the workstation will not create that capture by probing an unknown ECU.

    How to take the capture in the real app
    1. Connect a CAN adapter to the bike's OBD socket and your laptop. Nothing else should be talking on the bus.
    2. Start logging — SavvyCAN: connect, File → Log To File, run a GuzziCanDiag session (identify + live data is plenty), stop and export as CSV. socketcan: candump -tz can0 > capture.log.
    3. Analyse the file here. A minute of a live session is enough.

    K-Line identifier discovery

    The 5AM table is capture-verified; 16M now has documented legacy registers, 7SM has captured identification only, and MIU G3 has OEM identifier names without enough framing or scaling to execute them. Other families remain blocked. This offline research tool reads an existing capture, reports identifiers that answered, and — given a reference CSV recorded at the same time — tests possible scalings instead of guessing. Its output does not enable a motorcycle profile by itself.

    How to take the capture in the real app
    1. Tap the K-Line between the adapter and the laptop (a second FTDI on the same line, or a logging passthrough) and log everything while GuzziDiag or IAWDiag runs a normal live-data session on the bike.
    2. In that tool, log its own values to CSV over the same minutes. That second file is what turns "0x42 answered" into "0x42 is battery volts × 0.01".
    3. Sweep the engine through its range while logging: a value that never moves cannot be solved, and will be reported as unsolved rather than invented.
    4. Analyse both here. Nothing is written to the catalog automatically — you get a draft to check.

    ECU memory

    Reading an ECU image is slow but safe. Writing one is neither. Everything here is ordered the way it has to happen: check the adapter, read a backup, verify it, validate the new image, and only then write.

    Connect to an ECU first.

    1 · Adapter pre-flight

    A 16 ms FTDI latency timer is the usual reason a 20 minute read takes hours. GuzziDiag calls 1 ms essential. On Windows, if the adapter shows no COM port at all, the check points you at the WHQL driver bundle mirrored with the project; KKL adapters are FT232-based.

    Not checked.

    2 · Backup

    A backup is read twice and only kept if both reads agree byte for byte. One read over a noisy K-Line is not a backup.

    2b · Base map (mandatory before any write)

    The base map is the untouched calibration this bike arrived with, filed in its own vault with its SHA‑256. A verified backup saves one automatically; it is re‑hashed before every write, and a write is refused without it. Later backups become extra restore points — the original is never overwritten.

    Connect to an ECU first.

    3 · Validate an image

    Size, vector table, entropy and hardware family are checked before a single byte is sent. Flashing an HW1xx image into an HW3xx ECU bricks it.

    Maps & tables

    Render a dump as named fuel and ignition tables with a TunerPro XDF definition — all 94 cataloged GuzziDiag definitions ship bundled. Drop .xdf files into ~/.guzzionboard/xdfs/ to correct or extend them. Rendering and comparison are read-only; the advanced builder below always writes a new file and never changes its source.

    The chooser is grouped by motorcycle, not by the title the definition's author happened to type: definitions for the ECU family on the bench come first, everything else is listed under the bikes it was published for and marked as not matching. Picking a map from the wrong family does not give slightly wrong numbers — it reads a different calibration layout at the same addresses. A mismatched definition can be viewed, but the builder refuses to use it.

    Physical validation not established

    Software tests and simulation are not real-ECU or dyno evidence. See docs/PHYSICAL_VALIDATION.md and load hashed operator records through the validation registry.

    Advanced · Evidence-backed map builder

    Load a map, select known values, then double-click or use the transformation tools to stage changes. Every build needs an inspectable recommendation, previews the exact quantized plan, records source/XDF/plan/output hashes and byte changes, and requires the liability acknowledgement below. No fuel, spark, lambda or limiter recommendations are invented or bundled by this app.
