## Two additional links: source checked 2026-10-31

### OpenETV — actual torque-map mathematics

[OpenETV at 6b781e4fc11e5994531c367eb897f16d1a33318f](https://github.com/silviosackewitz-code/OpenETV/tree/6b781e4fc11e5994531c367eb897f16d1a33318f), MIT, copyright Silvio Sackewitz. Inspected `rust/src/model.rs`, `formats.rs`, `grid.rs`, `batch.rs`, `rust/tests/numerics.rs`, and the manual. The code models engine torque vs RPM/throttle and rider torque request vs RPM/grip, performs bilinear lookup and interpolation across nonzero engine rows, inverts torque to throttle, identifies saturation/below-minimum/non-monotonic results, and handles clamped RPM. It also implements request generation, reversal and table fixes; its formats code handles CSV, DSS XML and spreadsheets. These are real calculations, not ECU communications. Its own warning says the result needs dyno validation and does not validate the actuator or ECU control strategies.

GuzziOnBoard now has an **offline local-browser/desktop research calculator** in Tools. `web/openetv-research.js` adapts the inversion and status logic, retaining attribution in `LICENSES/OpenETV-MIT.txt`; it accepts bounded strictly ordered numeric CSV tables, outputs throttle and per-cell status CSV, flags clamped engine RPM, clears stale output when edited, and rejects an entirely zero engine table. It deliberately does not implement OpenETV's full project, editing, DSS, spreadsheet, generation or smoothing workflows. Synthetic browser tests only; it does not establish table meaning, fitment, safety, nor produce an ECU image or transmit/write anything. No upstream sample maps, fonts, icons or binaries copied.

### Suzuki SDS–OBD gateway — protocol and implementation

[sunsided/suzuki-sds-obdii-gateway at 20644c2e21ca2a867e086409c7f130230a7327d7](https://github.com/sunsided/suzuki-sds-obdii-gateway/tree/20644c2e21ca2a867e086409c7f130230a7327d7) has real Rust code: `crates/sds/src/{frame,services,session,data,dtc}.rs`, `crates/obd/src/{isotp,pid,server}.rs`, and `firmware/src/tasks/{sds_poller,obd_server}.rs`. Cargo metadata declares `MIT OR Apache-2.0`, but this checkout contains no license text or named copyright notice; no source has been copied. The project aims at a 2017 V-Strom DL650XAL7 and **explicitly says nothing has been verified against the bike**. Its host tests validate codecs with synthetic vectors, not hardware. It builds SDS 10,400-baud K-Line startup and `21 08` sensor requests, converts candidate SDS values to a CAN OBD server, and also implements candidate DTC read/clear. The candidate sensor offsets are explicitly low-confidence and DTC stride/parameters unverified.

Code details relevant before any reuse: `Session::on_frame` accepts a response when either the target or source matches (not both); `dtc::parse` can return an incomplete list for a truncated declared count; firmware config explicitly describes an open Wi-Fi AP and uses a synthetic VIN. The server can request a fault clear. None of those behaviors was imported or enabled here. GuzziOnBoard now exposes only a separately selected **2017 V-Strom DL650XAL7 raw SDS research attempt**, with exact `C1 EA 8F` initialization, strict response address/service/checksum checks and bounded raw `21 08` data. No conversion, OBD gateway, DTC clear, memory access, ECU identification or tune is claimed. Our integration is synthetic-tested only, just as the source explicitly reports its own bike verification is outstanding.

## 5AM reader: source-code discrepancy and desktop correction

Rechecked [Vasiy/onboard-logger `e301fc40000aad418125ded215a074c25135c327`](https://github.com/Vasiy/onboard-logger/tree/e301fc40000aad418125ded215a074c25135c327), specifically `app/kline/{flasher,transport,fw_codec,params}.py`, `tests/test_flasher.py`, `docs/PROTOCOL.md`, `THIRD_PARTY.md`, and [DoI's `5am_util` mirror `73ba179513bf750004e9e06e6262d94d6c300260`](https://github.com/denandz/5am_util/tree/73ba179513bf750004e9e06e6262d94d6c300260), `main.c`. Onboard-logger is MIT with BSD-3-Clause notices for the 5am_util-derived routines. It reports completed writes on a Guzzi HW610 via USB and native UART using the original utility. Its newer framed Python flasher is stated to be **not yet wired in**; its tests use a scripted ECU, not physical execution. This is meaningful source-reported experience, but not a hardware test of GuzziOnBoard.

The two source readers send the 5AM read rate change from tester `01`, switch the UART to **64200** after the response, select each 16 KiB page with `36 11 00 FE 02 01 <block>`, and issue `36 21 00 <offset16> 20` with offset `4000..7FE0` for each page. They fill pages 2–5 with `FF` instead of fetching them. Our old physical path sent the baud-change command from `F1`, never changed the serial baud, selected only block 0 once, and then interpreted the read address as a continuous bank. Its simulator modeled that different behavior, so synthetic test success did not establish hardware compatibility. The source's full file contains 20 pages; the GuzziOnBoard region starts at page 1 and covers 19, with pages 2–5 still placeholders. `onboard-logger` checks the service/subfunction and response length, but its new flasher does not verify the remaining response metadata against the requested address/page; repeated matching output does not establish that association.

The desktop physical 5AM path now sends the correct source address, waits after acceptance and switches the UART; it selects each source page and returns a region-shaped **experimental partial read** with explicit FF-placeholder metadata. The read holds the diagnostic session lock to prevent concurrent polling/keepalive exchanges from interleaving; reconnect after the rate-switched read before another operation. It cannot be automatically shared as a qualifying completed memory read, treated as a verified backup/base map, or validated as a flash image while its sidecar is present. The simulator retains its existing contiguous model and is identified as synthetic; it is not evidence of this new physical path. Source-derived tests exercise page order, window resets, malformed replies, baud source/timing, failure on rejected switches, partial-image metadata and sidecar validation. No physical adapter or ECU has been tested here. The source's write success is not transferred to our write path; in particular its write path changes baud as well, and a complete physical write/recovery/readback integration still requires work.
